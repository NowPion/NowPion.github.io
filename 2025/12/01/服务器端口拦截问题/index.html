Docker 绕过防火墙的端口映射问题

问题发现

早上检查服务器时发现他妈的数据库被黑了，排查后才想起防火墙端口忘记关闭。立即登录服务器关闭了防火墙对应端口。

但远程测试时发现：端口居然还能连上！

问题原因

我的数据库服务是通过 Docker 启动的，这正是问题的根源。

Docker 默认把所有转发到容器的流量全部放行，无条件 ACCEPT。

Docker 的 iptables 行为

Docker 默认会在系统 iptables 中自动添加 NAT/FORWARD 规则，将映射端口直接放行。外部流量会绕过 INPUT 链，因此即使防火墙（UFW）没有开放端口，也能访问容器服务。

当 Docker 启动容器并映射端口（如 -p 3307:3306，等价于 -p 0.0.0.0:3307:3306）时，会自动执行以下操作：

  1. 在 nat/PREROUTING 链挂上 DOCKER 跳转，再由 nat/DOCKER 链添加 DNAT 规则，把宿主机端口转发到容器 IP 端口
  2. 在 filter/FORWARD 链插入 DOCKER-USER 和 DOCKER 跳转，由 filter/DOCKER 链添加 ACCEPT 规则，放行转发流量

由于流量不经过 INPUT 链，所以即使 UFW 禁止了端口，Docker 映射的端口仍然可以被外部访问。

注意 DOCKER-USER 链在 FORWARD 里的位置排在 DOCKER 链之前——这正是它能用来做白名单的原因：你写的 DROP 规则会先于 Docker 自动生成的 ACCEPT 被命中。

为什么绑定 127.0.0.1 就不一样

如果映射写成 -p 127.0.0.1:3307:3306，情况完全不同：

  1. DNAT 规则带上了 -d 127.0.0.1/32 的匹配条件，公网来的报文目的地址是你的公网 IP，匹配不上任何 DNAT 规则
  2. 匹配不上 DNAT，报文就还是「发给宿主机本机端口」的报文，正常走 INPUT 链，UFW 规则生效
  3. 退一步说，就算 UFW 放行了，docker-proxy 也只在 127.0.0.1:3307 上监听，公网 IP 上压根没有监听进程，照样连不上

这就是后面方案一为什么是首选的原因——一行参数，零副作用。

方案一：端口只绑回环地址（推荐，最小改动）

方案二：在 DOCKER-USER 链上做白名单（推荐）

DOCKER-USER 是 Docker 官方预留的自定义链，挂在 FORWARD 链的最前面，优先级高于 Docker 自己写的 ACCEPT 规则，是放自定义规则的唯一正确位置。

后果 说明
容器出不了网 Docker 不再写 POSTROUTING 的 MASQUERADE 规则，容器发的包没有源地址转换，直接回不来
容器间跨网段不通 DOCKER-ISOLATION-STAGE-* 链不再创建，自定义 bridge 网络之间的隔离和转发全乱
端口发布变成用户态代理 端口实际由 docker-proxy 用户态进程转发，性能下降、连接数受限于进程模型
要手写全套 NAT 每次新建容器网络都得自己补 MASQUERADE 和 DNAT

总结

Docker 默认的 iptables 管理机制虽然方便，但会绕过系统防火墙，带来安全隐患。生产环境建议：

  1. 敏感服务不要直接映射到公网，端口绑定写成 127.0.0.1:宿主机端口:容器端口，对外访问走反向代理
  2. 需要放行公网时，用 DOCKER-USER 链做源 IP 白名单，并做好规则持久化
  3. iptables: false 是最后手段，会破坏容器网络，非必要不用

安全无小事，别等被黑了才想起来补救。
